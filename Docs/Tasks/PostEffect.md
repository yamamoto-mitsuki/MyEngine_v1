## 決めたこと

| 決めたこと | 理由 |
|---|---|
| 将来はHDRで描画する | 4Kなどの高画質を再現できるようにしたい |
| HDRレンダリングを先にやり、HDR出力は後にする | HDRレンダリング（内部をfloatで計算し、トーンマッピングで収める）は、普通のSDRモニタでも画質が上がる。HDR出力は対応モニタとOS設定が必要 |
| HDRにしてもライティングはリニア空間のまま | HDRとリニア空間は対立しない。変わるのは「計算結果の置き場（1.0で頭打ちになるか）」と「最後にモニタへ出す部分」だけ |
| 4KとHDRは別々に進める | 4Kは解像度、HDRは明るさの幅の話。4KのSDRも、1080pのHDRもありうる |
| 描画サイズは「上限を上げる（4K固定）」ではなく「出力先と同じ大きさにする」 | 4K固定だと、1280×720のビューで9倍のピクセルを描くことになる。Bloomの縮小テクスチャも全部大きくなる |
| GameビューにはBloomをかける | Gameビューは製品版で見える絵なので、演出はここで確認する（`Editor.md`） |

## Bloomの仕組み（AIが実装した部分の解説）

### 関係するファイル
| ファイル | 役割 |
|---|---|
| `MyEngine/Engine.cpp:95` | 初期化の入口。`SceneRenderer::InitializePost(1920, 1080)` |
| `Graphics/Renderer/SceneRenderer.cpp` | 1回分の描画の流れ（3D → ポストエフェクト → UI） |
| `Graphics/PostEffect/PostProcess.cpp` | まとめ役。Bloom → Lensの順番、ON/OFF、調整値の反映 |
| `Graphics/PostEffect/BloomPass.cpp` | Bloom本体。テクスチャ・PSO・定数バッファの作成と各パスの実行 |
| `Shader/Data/Post/Fullscreen.VS.shader` | 頂点バッファなしで画面全体を覆う三角形を出す |
| `Shader/Data/Post/Bloom.hlsli.shader` | 定数バッファの構造体と、3×3ぼかし（テントフィルタ） |
| `BloomBright` / `BloomDown` / `BloomUp` / `BloomComposite` `.PS.shader` | 各パスの処理 |
| `Editor/EditorViewport.cpp:76-77`、`Window/WindowManager.cpp:183` | 呼び出し元（SceneビューはBloomなし、Gameビューとウィンドウはあり） |
| `Window/WindowManager.cpp:243` | フレーム末に定数バッファの書き込み位置をリセット |

### 初期化の順番
1. `SceneRenderer::InitializePost`
   - `postRT_`（SDR、1920×1080、深度あり）：3Dシーンの描き込み先
   - `PostProcess::Initialize` を呼ぶ
2. `PostProcess::Initialize`
   - `work_`（SDR）：Bloom合成の結果の置き場
   - Bloom・Lensの初期化、GlobalVariablesへの登録と保存値の読み込み
3. `BloomPass::Initialize`
   - 縮小用テクスチャを2列作る（すべてHDR = float）
     - `down_`：960×540 → 480×270 → 240×135 → 120×67
     - `up_`：同じ大きさで4枚
   - 定数バッファ：256バイト × 32スロット
   - PSO 4つ（Bright / Down / Upの出力はfloat、Compositeの出力はSDR）

### 毎フレームの順番（Gameビューの場合）
1. `postRT_` に3Dだけを描く（不透明 → Skybox → 半透明 → Line → Particle）
2. `PostProcess::Prepare`
   1. GlobalVariablesの値を反映する
   2. `BloomPass::Record` で光の層を作る
      - **Bright**：`postRT_` → `down_[0]`
      - **Down × 3**：`down_[0]` → `[1]` → `[2]` → `[3]`
      - **Up × 3**
        - `down_[3]` をぼかして拡大し、`down_[2]` を足す → `up_[2]`
        - `up_[2]` をぼかして拡大し、`down_[1]` を足す → `up_[1]`
        - `up_[1]` をぼかして拡大し、`down_[0]` を足す → `up_[0]`
   3. `work_` に **Composite**：シーン + `up_[0]` × 強さ
3. 描画先（`gameRT_` やウィンドウ）に `LensPass` で最終出力する（入力は `work_`）
4. UI（2D）を上に重ねる（ポストエフェクトの外なので、ぼけも歪みもしない）
5. フレーム末に `ResetViewIndex` で、Bloomの定数バッファの書き込み位置を0に戻す

1回の描画で使うパスは 1 + 3 + 3 + 1 = **8**。コマンドは後でまとめて実行されるので、パスごとに別のスロットへ定数を書く必要がある。

### 各パスでやっていること
- **Bright（明るい所だけ抜き出す）**
  - 明るさは「R・G・Bのうち一番大きい値」
  - `Threshold` を超えた分だけ残す。境目でバッサリ切るとチラつくので、`Knee` の幅だけ二次曲線でなだらかにつなぐ
  - 最後に元の明るさで割って色に掛けるので、色味の比率は保ったまま明るさだけを削る
  - 半分の解像度に書くと、出力ピクセルの中心が元の2×2ピクセルの角に来るので、1回のサンプルで4ピクセルの平均が取れる
- **Down（縮めながらぼかす）**
  - 重み 1-2-1 / 2-4-2 / 1-2-1（合計16で割る）の3×3でぼかす
  - 1段ごとに解像度が半分になるので、同じ3×3でも元の画面で見たぼける範囲が倍々に広がる。安いコストで広くぼかすための仕組み
- **Up（戻しながら重ねる）**
  - 小さい段をぼかして1段大きくし、同じ大きさの `down_` の結果を足す
  - 狭いにじみ（大きい段）から広いにじみ（小さい段）まで全部重なるので、光が自然に広がって見える
  - 読んでいるテクスチャには同時に書き込めないので、`up_` を `down_` と別に持っている
- **Composite（合成）**
  - `シーン + Bloom × Intensity`。出力はSDRなので1.0で頭打ち
- （Bloomの後の **Lens**：歪み → 色収差 → 放射ブラー → ビネット）

### 調整項目
- GlobalVariablesの `PostEffect / Bloom`：`Enabled`、`Threshold`（0.75）、`Knee`（0.25）、`Intensity`（0.9）
- `addIntensity` / `addThreshold`：ゲーム側から一時的に上乗せするための変数。**今はどこからも使われていないので常に0**

## 問題点・未解決

### 1. Bloomへの入力が1.0で頭打ちになっている
- `postRT_` も `work_` もSDR（`R8G8B8A8_UNORM_SRGB`）。
- `Threshold 0.75` だと、光るのは明るさ0.75〜1.0の範囲だけ。「明るさ1.0の場所」と「明るさ10の場所」を区別できないので、Bloomの効きが本来より弱い。
- → 予定1（HDRレンダリング）で解決する。そのときCompositeのPSOの出力形式も合わせて変える。

### 2. 描画サイズが1920×1080で固定されている
- `postRT_` は起動時（`Engine.cpp:95`）に1回だけ作られ、その後変わらない。3Dは出力先の大きさに関係なく常に1920×1080で描かれ、最後のLensで出力先の大きさに縮小・拡大される。

| 出力先 | 実際の処理 | 起きること |
|---|---|---|
| Gameビュー 1280×720 | 1920×1080で描いて縮小 | 見えない分まで描いていて無駄（約2.25倍） |
| ウィンドウ 1920×1080 | そのまま | 問題なし |
| ウィンドウ 2560×1440 / 4K | 1920×1080で描いて拡大 | **ぼやける。4Kで表示しても中身は1080p** |

- Gameビュー自体のサイズも `EditorViewport.cpp:12-13` で1280×720に固定されている。
- → 予定3で解決する。

### 3. 描画サイズを可変にするときに解決すること
1. **出力先ごとに `postRT_` とPostProcessを持たせる**
   - 今は全部の出力先で1つだけ共有している。Gameビュー（1280×720）とウィンドウ（1920×1080）は同じフレームに描かれるので、共有したまま大きさを合わせると毎フレーム作り直すことになる。
2. **RenderTextureに作り直す仕組みを作る**
   - `RenderWindow::Resize` はあるが、RenderTextureには無い。
   - GPUが使っている最中のテクスチャを消すと落ちるので、作り直しはフレームの境目で行う（`WindowManager.cpp:261` でスワップチェーンをリサイズしているのと同じタイミング）。
   - 作り直したときにSRVスロットが解放されるかも確認する。
3. **Bloomの縮小テクスチャも一緒に作り直す**

### 4. `up_[3]` が使われていない
- `BloomPass::Initialize` で作っているが、Upのループは `up_[2]` から始まるので一度も使われない。消してよい。

### 5. 1フレームにBloomを使えるビューは4つまで
- 1ビュー8パス、上限 `kMaxPassPerFrame = 32`。`SceneRenderer` の `kMaxViewsPerFrame = 4` と一致しているので今は問題ない。
- どちらかを変えるときは両方そろえる。

### 6. ギズモにBloom / Lensがかかる
- ギズモがポストエフェクトより前に描かれているのが原因。詳細は `Editor.md` の「未解決」。

## HDR化の手順（予定1・2・5の中身）

### 用語
- **HDRレンダリング**：描画先をfloat（`R16G16B16A16_FLOAT`）にして、1.0を超える明るさを残したまま計算する。最後にトーンマッピングで表示できる範囲に収める。SDRモニタでも画質が上がる。
- **HDR出力（HDR10）**：HDR対応モニタへ、1.0を超える明るさのまま送る。スワップチェーンの形式と色空間の設定変更が必要。

### 今の対応状況
| もの | 形式 |
|---|---|
| IBLのキューブマップ、Skybox、Bloomの縮小テクスチャ | float（HDR） |
| `postRT_`（SceneRenderer）、`work_`（PostProcess）、`sceneRT_` / `gameRT_`（EditorViewport） | SDR |
| トーンマッピング | 無い |
| スワップチェーン | `R8G8B8A8_UNORM`（RTVは `_SRGB`） |

### 手順
1. `postRT_` と `work_` をfloatにする（CompositeのPSOの出力形式も変える）
2. Bloom合成の後、最終出力の前に、トーンマッピングと露出のパスを追加する
3. トーンマッピングの結果を、今の `_SRGB` 出力のまま画面に出す。**ここまでで普通のモニタでも画質が大きく上がる**
4. HDR出力に対応する
   - スワップチェーンを `R10G10B10A2` + PQ色空間（またはfloat + scRGB）にする
   - モニタがHDRに対応しているか確認する
   - ImGuiを合成するときの明るさを調整する

### Light側との関係
- ライトの色はsRGBでComponentに持ち、GPUへ送るときにリニアへ変換する（`Light.md` Step 5）。HDRにしてもこの形は変わらない。
- ライトの明るさ（1.0超え）は `intensity` で表す。HDRレンダリングにして初めて、1.0を超えた分がBloomとトーンマッピングに正しく反映される。
